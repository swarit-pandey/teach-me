Tokenization

A language model never sees text. It sees a list of integers. Tokenization is the step that turns a string into that list, and the choice of tokenizer quietly decides the model's vocabulary size, how long its sequences are, what it finds easy and what it finds bizarrely hard. Byte-pair encoding, the algorithm behind GPT, is about thirty lines of code, and you'll write it.

By the end you can

  • Compare character, word and subword tokenization by vocabulary size, sequence length and out-of-vocabulary behaviour.
  • Run byte-pair encoding (BPE) training by hand, and encode/decode new text with a learned merge table.
  • Reason about the vocabulary-size trade-off: embedding parameters versus sequence length versus attention cost.
  • Explain byte-level BPE, UTF-8, pre-tokenization, and the strange behaviours they cause (numbers, leading spaces, other languages, letter counting).

    1. Why tokenize at all?

    Everything a neural network does is arithmetic on vectors. In lesson 20 you fed a model text by giving each character an integer id and looking up a learned embedding vector for each id. That step, string → list of ids, is tokenization. The pieces are tokens, the set of possible pieces is the vocabulary, and its size is $V$.

    The model's whole interface is built around $V$:

    • The input embedding table is a $V \times d$ matrix: one row per token (lesson 20).
    • The output layer produces $V$ logits, turned into a next-token distribution by softmax (lesson 14) and trained with cross-entropy (lesson 11).
    • Everything in between (attention, lesson 22) runs on a sequence of $n$ tokens. Attention compares every token with every other token, so its cost grows like $n^2$.

    So the tokenizer controls two numbers that pull against each other. A larger vocabulary means bigger tables but shorter sequences. A smaller one means tiny tables but long sequences. The rest of this lesson is about where to sit on that dial, and how byte-pair encoding gets there automatically.

    Think of a tokenizer as a compression scheme the model has to read in. A good one turns frequent chunks like " the" or "ing" into single symbols, so the model spends its limited context window and compute on meaning rather than on spelling.

    2. Characters, words, or something in between

    There are three natural choices.

    UnitVocabularySequence lengthUnseen input
    Characters (or bytes)tiny: ~100 characters, or exactly 256 byteslong: one token per characternever a problem
    Wordshuge: English alone has hundreds of thousands of word formsshorta new word, typo or name becomes [UNK], and its meaning is lost
    Subwordschosen: typically 30k–200kmedium: about 4 characters per token in Englishrare words are spelled out of smaller known pieces

    Subwords get the best of both. Common words are one token. Rare words are split into a few common pieces ("unbeliev" + "ably"). And if the smallest pieces are single bytes, nothing is ever out of vocabulary.

    Try it: pick an example or type your own text. The word tokenizer only knows the ~500 words and symbols in a short Shakespeare excerpt, so anything else becomes [UNK]. The subword tokenizer was trained on the same excerpt (byte-level BPE with 480 merges, section 3) and can still spell anything. Compare the token counts. Try a typo like "citizzens" or a word in another language.

    3. Byte-pair encoding: learning the vocabulary

    Byte-pair encoding (BPE) started as a 1994 compression algorithm. Sennrich et al. adapted it for machine translation in 2016, and GPT-2 made the byte-level version standard. The idea fits in one sentence: start from single bytes and repeatedly glue together the most frequent adjacent pair.

    Concretely, with the text as a list of ids (initially its UTF-8 bytes, ids 0–255):

    1. Count every adjacent pair $(a, b)$ in the sequence.
    2. Take the most frequent pair. Give it a new id: 256 for the first merge, 257 for the next, and so on. Record the rule $(a, b) \to$ new id in the merge table.
    3. Replace every occurrence of $a, b$ in the sequence by the new id, scanning left to right.
    4. Repeat until the vocabulary reaches the size you want (or no pair occurs twice).

    The vocabulary is then the 256 bytes plus one token per merge. Each token stands for a fixed byte string: the concatenation of the two tokens it was made from.

    Worked example: training

    Text aaabdaaabac: 11 bytes, written with letters for readability (a = 97, b = 98, c = 99, d = 100).

    Step 1. Pair counts: aa: 4, ab: 2, and bd da ba ac: 1 each. Merge aa → id 256. Scanning left to right, aaa becomes [aa] a, because matches can't overlap. Sequence: [aa] a b d [aa] a b a c, 9 tokens.

    Step 2. Counts: ([aa], a): 2 and (a, b): 2 tie. We break ties by first appearance, so ([aa], a) → 257 = "aaa". Sequence: [aaa] b d [aaa] b a c, 7 tokens.

    Step 3. ([aaa], b): 2 → 258 = "aaab". Sequence: [aaab] d [aaab] a c, 5 tokens.

    Step 4. Every pair now occurs once. Merging a pair that occurs once saves nothing, so we stop. Result: 3 merges, 11 bytes → 5 tokens, a compression ratio of 11/5 = 2.2 bytes per token.

    Try it: press Step to run one merge, or Play. The bar chart shows the pair counts before the next merge, and the winning pair is highlighted. Watch the sequence shrink and the merge table grow. In the "low / lower / newest / widest" text, notice that est forms before low: it is shared by "newest" and "widest", so it is more frequent. Each merge shortens the sequence by the number of places it fires, which equals the pair's count unless occurrences overlap (as in aaa).

    Every merge shortens the training sequence by the number of (non-overlapping) places it fires, usually its count, which is at least 2. BPE is a greedy compressor: at each step it makes the single merge that shrinks the corpus most. It never looks ahead, and it never undoes a merge.

    4. Encoding and decoding new text

    Decoding is trivial. Look up each id's byte string, concatenate, and decode the bytes as UTF-8. Encoding a new string has one subtlety: you must replay the merges in the order they were learned. Merge 258 ([aaa] b) was learned on a sequence where merges 256 and 257 had already happened, so it can only ever fire on their outputs. The standard procedure is:

    1. Start from the bytes of the string.
    2. Among the adjacent pairs present, find the one with the lowest merge id (the earliest learned). If no present pair is in the table, stop.
    3. Merge it everywhere and go to 2.
    Worked example: encoding

    With the merges from section 3 (256 = aa, 257 = aaa, 258 = aaab), encode daaab:

    d a a a b → the earliest merge present is aa (256) → d [aa] a b → ([aa], a) is 257 → d [aaa] b → ([aaa], b) is 258 → d [aaab]. Two tokens.

    Now aaaab: a a a a b → aa merges twice, left to right → [aa] [aa] b. No pair of these is in the table, so we stop at three tokens, even though "aaab" is in the vocabulary. BPE encoding is deterministic and greedy. It doesn't search for the shortest tokenization. The same substring can therefore be tokenized differently depending on what surrounds it, which is one source of tokenizer oddities (section 7).

    Applying merges in the wrong order silently produces ids the model never saw in training. With the table (b, c) → 256 learned first and (a, b) → 257 second, the string abc must become a [bc]. Greedily merging ab first would give [ab] c, a sequence that never appeared in training. The workbook has a test for exactly this.

    Round-tripping is guaranteed. Every merge replaces two tokens with one token whose byte string is their concatenation, so the concatenated bytes of the sequence never change. Hence $\text{decode}(\text{encode}(s)) = s$ for every string (problem 5). The reverse is not true. Many id sequences decode to the same string ("aa"+"a" vs "a"+"aa"), and only one of them is what encode produces.

    5. Choosing the vocabulary size

    More merges means more compression, but with diminishing returns. The first merges capture " t", "he", " the" and save a lot. Late merges capture rare words and save little. Meanwhile each extra token costs a row in the embedding table and a column in the output layer.

    Try it: slide the vocabulary size. The blue curve is compression (UTF-8 bytes per token) on the 6,500 characters the tokenizer was trained on. The orange curve is the same measure on 1,500 characters it never saw. The gap widens as merges get more specific to the training text: late merges memorize rare words. The sentence below is re-tokenized live, so you can watch pieces fuse into words.

    The trade-off, with $N$ the number of bytes of text, $r$ the compression ratio (bytes per token) and $d$ the model width:

    $$n = N / r \;\text{tokens}, \qquad \text{embedding params} = V d, \qquad \text{attention cost} \propto n^2 = N^2 / r^2.$$

    Doubling $r$ halves the sequence. That halves the cost of every per-token layer, quarters the attention cost, and doubles how much text fits in a fixed context window. Real models sit at $V$ = 50,257 (GPT-2), about 100k (GPT-4) and about 128k (Llama 3), and get about 4 bytes per token on English. A larger $V$ also makes each softmax over the vocabulary more expensive, and leaves many rare tokens with too few training examples to learn good embeddings.

    Worked example: what the embedding table costs

    GPT-2 small: $V$ = 50,257 and $d$ = 768. The embedding table has $50{,}257 \times 768 = 38{,}597{,}376$ parameters, about 31% of the model's 124M. (GPT-2 reuses the same matrix for the output layer, called weight tying, otherwise it would be 62%.) A byte-level model with $V$ = 256 would need only 196,608 embedding parameters, but its sequences would be about 4× longer, so each context window would hold a quarter of the text.

    6. Byte-level BPE and UTF-8

    Unicode has about 150,000 assigned characters. If BPE started from characters, its base alphabet would be enormous, or rare characters would become [UNK]. GPT-2's trick is to start from bytes. Any string is first encoded as UTF-8, a variable-length code that uses:

    Code pointsBytesExamples
    U+0000 – U+007F1ASCII: a Z 0 ! space newline
    U+0080 – U+07FF2é, ß, ñ, Cyrillic, Greek, Arabic, Hebrew
    U+0800 – U+FFFF3Chinese, Japanese, Hindi (Devanagari), most other scripts
    U+10000 and up4emoji, rare CJK, historic scripts

    The base vocabulary is exactly the 256 byte values, so every possible string is representable and there is no [UNK] ever. The cost: text that BPE rarely saw in training stays close to raw bytes. A Chinese character is 3 tokens before any merges.

    Try it: type anything, or pick an example. Each box is one Unicode character: its code point, then its UTF-8 bytes in hex. Box colour shows the byte count (1 = blue, 2 = green, 3 = orange, 4 = pink). Note that 👍🏽 is two code points (thumbs-up plus a skin-tone modifier), 8 bytes in total. A string's "length" depends on whether you count characters, code points, bytes or tokens.

    Because tokens are byte strings, a token boundary can fall in the middle of a multi-byte character. Decoding a single such token gives an invalid byte sequence. That's why decode must use errors="replace" (it shows �), and why streaming chat interfaces sometimes buffer a token or two before printing.

    7. Pre-tokenization and tokenizer oddities

    Run plain BPE on raw text and it happily learns tokens like "e " (the end of one word plus the space before the next) or ":\n" that straddle words, spaces and punctuation. That wastes vocabulary on accidents. GPT-2 therefore first pre-tokenizes: a regular expression splits the text into chunks (a word with its leading space, a run of digits, a run of punctuation, whitespace), and merges are only allowed inside a chunk. The workbook uses a simplified version of GPT-2's pattern:

    's|'t|'re|'ve|'m|'ll|'d| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+

    The " ?" in front of letters is why the space belongs to the following word. The result is one of the most visible quirks of modern tokenizers:

    Try it: click through the examples. Each box is a token, with its id underneath (␣ marks a space, ↵ a newline). This tokenizer is tiny (480 merges on a Shakespeare excerpt), but real tokenizers show the same effects. the, ␣the, The and THE get unrelated ids. Numbers are split into arbitrary chunks. Non-English text costs several times more tokens per character.

    Real tokenizers show the same quirks at scale, and each one leaks into model behaviour:

    • Leading spaces and case. "the", " the", "The" and " The" are four unrelated ids. The model must learn separately that they mean the same thing. A prompt ending in a trailing space leaves the model in an unusual state, because in training the space was almost always glued to the next word.
    • Numbers. GPT-2 tokenized digit strings by frequency, so "1234" and "1235" might split as 12|34 and 123|5. Digit columns then don't line up, which makes arithmetic harder. Newer tokenizers split numbers into single digits or into groups of three.
    • Spelling. The model sees " strawberry" as one or two ids, not ten letters. "How many r's are in strawberry?" asks about information the model never directly saw. It has to have memorized each token's spelling.
    • Other languages. A tokenizer trained mostly on English compresses other languages poorly. The same sentence can take 2–10× more tokens in Hindi or Burmese than in English. That means a shorter effective context, slower generation and a higher price per word, sometimes called the "token tax".
    • Glitch tokens. If the tokenizer's training data differs from the model's, some tokens (GPT-2's famous " SolidGoldMagikarp", a Reddit username) almost never appear in model training. Their embeddings stay near random, and prompting with them produced bizarre output.

    In lesson 24 you'll train a GPT at character level ($V$ = 65) because it's simple and the vocabulary is tiny. Every production LLM uses byte-level BPE or a close cousin (SentencePiece's BPE/unigram). Tokenization also matters for RL fine-tuning (lessons 28–29). Rewards, KL penalties and log-probabilities are all computed per token. So "the policy's probability of this answer" means a product over the tokenizer's pieces, not over words.

    8. Problems

    Use pencil and paper for the hand-simulations. That is where BPE stops being magic.

    Problem 1
    warm-up

    How many bytes does the string naïve 🙂 take in UTF-8? (There is one space.)

    Solution

    n, a, v, e and the space are ASCII, 1 byte each: 5 bytes. ï is U+00EF, in the 2-byte range. 🙂 is U+1F642, above U+FFFF, so 4 bytes. Total 5 + 2 + 4 = 11 bytes for 7 characters.

    Problem 2
    warm-up

    Run two BPE merges (no pre-tokenization, ties broken by first appearance) on abababcab. Which two merges are learned, and how many tokens remain?

    Solution

    Pairs: ab ×4, ba ×2, bc, ca ×1. Merge ab → X: X X X c X (5 tokens). Now XX occurs twice (overlapping, counted at positions 1–2 and 2–3), and Xc, cX once. Merge XX → Y. Scanning left to right, the first two X's fuse and the third has no partner: Y X c X, which is 4 tokens. Note that a pair's count (2, overlapping) can exceed the number of merges actually made (1, non-overlapping).

    Problem 3
    core

    Using the merge table from the worked example (256 = aa, 257 = aaa, 258 = aaab), encode baaabaaaab. How many tokens do you get?

    Hint

    Always apply the earliest-learned merge that is present, everywhere at once, left to right. Then look again.

    Solution

    b a a a b a a a a b. Merge aa everywhere (left to right): b [aa] a b [aa] [aa] b. Now ([aa], a) is present once: b [aaa] b [aa] [aa] b. Then ([aaa], b): b [aaab] [aa] [aa] b. No pair left is in the table, so we have 5 tokens. The second "aaaab" didn't become "a" + "aaab", because aa was already glued from the left.

    Problem 4
    core

    A model has vocabulary $V$ = 50,257 and width $d$ = 768. How many parameters are in its token-embedding table? If the output layer is a separate (untied) $d \times V$ matrix, how many parameters do the two together have?

    Enter both, comma-separated:

    Solution

    $50{,}257 \times 768 = 38{,}597{,}376$, and twice that is $77{,}194{,}752$. For a 124M-parameter model, an untied output layer would make the vocabulary account for about 62% of all parameters. That's why small models tie the two matrices.

    Problem 5
    core · proof

    Prove that $\text{decode}(\text{encode}(s)) = s$ for every string $s$ and every merge table produced by training.

    Hint

    Find a quantity that no merge changes: an invariant.

    Solution

    Let $B(t)$ be the byte string a token $t$ stands for, and for a sequence define $B(t_1 \dots t_n) = B(t_1)\Vert\cdots\Vert B(t_n)$ (concatenation). Initially the sequence is the bytes of $s$, so $B = \text{utf8}(s)$. A merge replaces adjacent $a, b$ by $c$ with $B(c) = B(a)\Vert B(b)$ by construction of the vocabulary. Concatenation is associative, so $B$ of the whole sequence is unchanged. By induction over the merges, $B(\text{encode}(s)) = \text{utf8}(s)$. Decoding computes $B$ and then UTF-8-decodes it, which recovers $s$ exactly because $\text{utf8}(s)$ is valid UTF-8. $\blacksquare$

    Problem 6
    core

    You switch a model from byte-level input (1 byte per token) to a BPE tokenizer averaging 4 bytes per token, with the same context window in bytes. By what factor does the cost of computing all attention scores (proportional to $n^2$) fall?

    Solution

    $n$ falls by a factor of 4, so $n^2$ falls by $4^2 = 16$. Per-token costs (embeddings, MLPs) fall by 4. Equivalently, at fixed compute the model can read about 4× more text per window. That is the main reason byte-level LLMs remain a research topic rather than the default.

    Problem 7
    stretch · proof

    Show that after $k$ merges no token is longer than $2^k$ bytes, and that this bound is tight. What is the bound for $k = 10$?

    Hint

    Induction: every new token is two existing tokens glued together. For tightness, try a text made of a single repeated letter.

    Solution

    Let $L_k$ be the longest token length after $k$ merges, with $L_0 = 1$ (single bytes). Merge $k+1$ creates a token $B(a)\Vert B(b)$ whose two parts are each at most $L_k$ long, so $L_{k+1} \le 2L_k$ and therefore $L_k \le 2^k$. For $k = 10$: 1024 bytes.

    Tightness: train on $\texttt{a}$ repeated $2^{k+1}$ times. The first merge is aa (count $2^{k+1}-1$), leaving $2^k$ copies of [aa]. The next merge is [aa][aa], leaving $2^{k-1}$ copies of a 4-byte token, and so on. Each round halves the number of copies and doubles the token length, and after $k$ rounds two copies of a $2^k$-byte token remain. In practice, long tokens come from long repeated strings in the training data: runs of spaces in code, separator lines like ----------, boilerplate licences.

    Problem 8
    core · conceptual

    Explain, in terms of tokens, why an LLM that writes fluent essays may fail to (a) count the r's in "strawberry", (b) reverse the string "tokenization", and (c) add two 12-digit numbers reliably. For each, suggest a prompt or tokenizer change that helps.

    Solution

    (a) "strawberry" arrives as one or a few ids. The letters are not in the input; the model must have learned each token's spelling as a fact. Fix: ask it to spell the word letter by letter first. Then each letter becomes its own token, and the counting runs over visible tokens. (b) Same issue. Reversal has to happen at the character level, while the model's units are multi-character chunks whose internal order it can't see. Spelling it out first also helps. (c) Multi-digit numbers are chunked by frequency, so place values don't line up between operands and the chunking changes with the digits. Fix: tokenizers that split numbers into single digits (or right-aligned groups of three), or prompting the model to write digits with separators.

    9. Quick check

    Why can a byte-level BPE tokenizer never produce an out-of-vocabulary token?
    In the worst case, a string never seen in training is encoded as raw bytes, one token each. Inefficient, but always representable.
    You double a tokenizer's vocabulary size (retraining BPE with more merges). What is most likely to happen?
    Compression has diminishing returns (the curve in section 5 flattens), so the sequence shrinks by much less than half. The table costs, though, scale linearly in $V$.
    In a GPT-2-style tokenizer, why do "dog" and " dog" usually have different ids?
    Tokens are byte strings, and the space is byte 32. Mid-sentence words almost always follow a space, so " dog" is the common form and "dog" (sentence start, after a quote or newline) is a separate, rarer token.
    Your encoder applies whichever merge appears most often in the new string first, instead of the earliest-learned merge. What goes wrong?
    Decoding still round-trips: any merge sequence preserves the bytes. But the model was trained on the canonical tokenization. A different segmentation of the same text is out-of-distribution input.

    10. Summary

    ConceptWhat to remember
    Tokenizationstring → list of ids from a vocabulary of size $V$. It fixes the embedding and output layers' size.
    BPE trainingstart from bytes; repeatedly merge the most frequent adjacent pair into a new id
    BPE encodingreplay merges, earliest-learned first; greedy and deterministic
    Round trip$\text{decode}(\text{encode}(s)) = s$, because merges preserve the concatenated bytes
    Vocab trade-offtokens $n = N/r$; embedding params $Vd$; attention $\propto n^2$; compression has diminishing returns
    Byte-level256-byte base alphabet means no [UNK]; UTF-8 uses 1–4 bytes per character
    Pre-tokenizationa regex split so merges stay inside words; the source of the leading-space tokens
