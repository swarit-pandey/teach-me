Moving to PyTorch

You've built every piece by hand: batched forward passes (lesson 16), an autograd engine (17), optimizers and LayerNorm (18). PyTorch is those same pieces, engineered: tensors that run on GPUs, an autograd engine that records tensor ops, and a library of modules and optimizers. Because you've built a toy version of each, nothing in this lesson is magic. It's mostly a mapping from your code to theirs, plus the habits that keep shapes and gradients sane.

By the end you can

  • Move between NumPy and torch tensors, and predict broadcasting and matmul shapes before running code.
  • Map requires_grad, grad_fn, .backward() and .grad onto your own micrograd.
  • Write nn.Modules with nn.Parameters, and the canonical five-line training loop with an optimizer and a DataLoader.
  • Debug shape errors systematically, and understand views, strides and .contiguous().
  • Write a custom autograd.Function and verify it with gradcheck.

    One important difference: PyTorch frees the graph after backward() to save memory. Call it twice on the same graph and you get an error, unless you pass retain_graph=True. Each training step builds a fresh graph, just as your micrograd did.

    2. Tensors and NumPy

    A tensor is an n-dimensional array: lesson 12's ndarray plus a device (CPU or GPU) and optional gradient tracking. The API is deliberately NumPy-like:

    a = np.arange(6.0).reshape(2, 3)
t = torch.from_numpy(a)      # shares memory with a: a[0,0] = 9 changes t too
t2 = torch.tensor(a)         # copies
back = t2.numpy()            # shares memory (CPU only); use t.detach().cpu().numpy() in general
t.dtype                      # torch.float64, inherited from numpy
torch.zeros(2, 3).dtype      # torch.float32: torch's default, numpy's is float64!
loss.item()                  # 0-d tensor -> Python float (detaches; use it for logging)

    Three classic first-week bugs. (1) Mixing float64 data from NumPy with float32 model weights gives "expected scalar type Float but found Double". Convert with .float(). (2) Logging total += loss instead of loss.item() keeps every step's graph alive and leaks memory. (3) Integer class labels must be torch.long (int64) for F.cross_entropy.

    Broadcasting and matmul shapes

    Broadcasting follows NumPy's rules exactly (lesson 12). Align the shapes on the right, and each pair of sizes must be equal or contain a 1, which stretches. @ (torch.matmul) treats the last two dimensions as matrices, $(\dots, n, k) @ (\dots, k, m) \to (\dots, n, m)$, and broadcasts all the leading "batch" dimensions. That one rule covers a batch of sequences of token vectors hitting a weight matrix, $(B, T, C) @ (C, V) \to (B, T, V)$. You'll see it in every transformer (lessons 22–24).

    Try it: pick an example, or type your own shapes (comma-separated) and press Enter. For +, sizes are compared column by column from the right. Green means equal, blue means one side is 1 and stretches, red means a mismatch. For @, the last two dims follow the matrix rule (the inner sizes must match) and the leading dims broadcast. Predict the result before you look.

    Views, strides and .contiguous()

    A tensor is a flat block of memory plus metadata: a shape, a stride (how many elements to skip in memory to move one step along each dimension), and an offset. Many operations (.T, .transpose, slicing, .view, .expand) just make new metadata over the same memory. They're free, but writing through them changes the original. .view() requires a compatible memory layout, while .reshape() copies when it must.

    Try it: the bottom row is the tensor's memory, 12 numbers in a line. The grid is the tensor as you index it. Choose an operation and hover over a cell to see which memory slot it reads, at address $\text{offset} + \sum_d i_d\cdot\text{stride}_d$. After .T the memory is untouched and only the strides swap, so the tensor is no longer "contiguous" (row-major). That's why x.T.view(-1) raises an error while x.T.contiguous().view(-1) works: .contiguous() copies into fresh row-major memory.

    3. Autograd: the graph PyTorch records

    Any tensor computed from a tensor with requires_grad=True gets a grad_fn: the backward node of the op that made it. Leaves you created yourself (your parameters) have grad_fn = None. They're accumulated into by special AccumulateGrad nodes, which do p.grad += incoming. Calling loss.backward() walks this graph in reverse topological order, exactly like your Value.backward.

    Try it: the graph PyTorch records for loss = ((x @ W + b).relu() - y).pow(2).mean(), with batch size $N$. Click any node to see its forward op, output shape and what its backward computes. Press backward step to walk the graph in reverse topological order, watching the gradient's shape at each edge. Notice AddBackward0: b was broadcast over $N$ rows, so its gradient gets summed back to shape (4,). Your unbroadcast from workbook 17 lives inside it.

    Three switches control recording. with torch.no_grad(): turns it off, which you want for evaluation and for manual parameter updates. t.detach() returns the same data cut out of the graph. model.eval() is unrelated to gradients: it switches layers like dropout and BatchNorm to inference behavior. You usually want both model.eval() and no_grad() when evaluating.

    4. nn.Module and nn.Parameter

    A module is an object that owns parameters and submodules and defines forward. Assigning an nn.Parameter or another module as an attribute registers it, so model.parameters() can find every learnable tensor recursively. That's how the optimizer knows what to update. Here is nn.Linear, essentially as PyTorch writes it:

    class MyLinear(nn.Module):
    def __init__(self, d_in, d_out):
        super().__init__()                                   # sets up the registries
        k = 1 / d_in ** 0.5
        self.weight = nn.Parameter(torch.empty(d_out, d_in).uniform_(-k, k))
        self.bias   = nn.Parameter(torch.empty(d_out).uniform_(-k, k))

    def forward(self, x):                                    # x: (..., d_in)
        return x @ self.weight.T + self.bias                 # (..., d_out)

class MLP(nn.Module):
    def __init__(self, sizes):
        super().__init__()
        self.layers = nn.ModuleList(MyLinear(a, b) for a, b in zip(sizes, sizes[1:]))
    def forward(self, x):
        for i, layer in enumerate(self.layers):
            x = layer(x)                                     # call the module, not .forward
            if i < len(self.layers) - 1:
                x = torch.relu(x)
        return x

    Notice PyTorch's weight convention: shape (d_out, d_in) and x @ W.T. In lessons 16–18 we used (d_in, d_out) and x @ W. Same math, transposed storage. Use nn.ModuleList or nn.Sequential, never a plain Python list, or the parameters silently go unregistered and never train. model.state_dict() is the dictionary of every registered tensor, which is what you save and load.

    Worked example: counting a model's parameters

    The character language model of lesson 20: nn.Embedding(65, 10), then nn.Linear(50, 100), then nn.Linear(100, 65).

    Embedding: a $65\times10$ table, so 650 parameters, no bias. First linear: $50\cdot100 + 100 = 5{,}100$. Second: $100\cdot65 + 65 = 6{,}565$. Total $12{,}315$, which is what sum(p.numel() for p in model.parameters()) prints.

    5. Optimizers and the canonical training loop

    Every PyTorch training script in the world contains these five lines:

    opt = torch.optim.AdamW(model.parameters(), lr=3e-4, weight_decay=0.1)
for xb, yb in loader:
    logits = model(xb)                      # 1. forward  (builds the graph)
    loss = F.cross_entropy(logits, yb)      # 2. loss     (a 0-d tensor)
    opt.zero_grad()                         # 3. clear .grad (it accumulates!)
    loss.backward()                         # 4. backward (fills p.grad)
    opt.step()                              # 5. update   (your lesson-18 Adam)

    F.cross_entropy takes raw logits and integer labels. It applies log-softmax internally, in the numerically stable way from lesson 14. Don't softmax first. Learning-rate schedules attach as torch.optim.lr_scheduler objects, stepped once per iteration.

    Try it: a small MLP trains in your browser with the five-line loop above, on a noisy spirals dataset split into 240 training and 60 validation points. Left: training and validation loss per epoch. Right: the data and decision regions. Explore: (1) SGD vs Adam at the same learning rate; (2) a learning rate that's too high, giving a spiky or diverging curve; (3) batch size 8 vs 240, which gives a noisy curve vs a smooth slow one; (4) hidden width 128 with long training, where validation loss turns back up (overfitting, lesson 15); (5) the forgot zero_grad() bug, where gradients pile up step after step and training goes haywire.

    6. Dataset and DataLoader

    A Dataset is anything with __len__ and __getitem__(i) returning one example. A DataLoader wraps it to produce shuffled minibatches. It draws indices, calls __getitem__ for each, and collates them by stacking the first elements into an xb of shape (B, ...) and the labels into yb.

    class Blobs(Dataset):
    def __init__(self, X, y):  self.X, self.y = torch.as_tensor(X).float(), torch.as_tensor(y).long()
    def __len__(self):         return len(self.y)
    def __getitem__(self, i):  return self.X[i], self.y[i]

loader = DataLoader(Blobs(X, y), batch_size=64, shuffle=True)   # reshuffled every epoch
xb, yb = next(iter(loader))                                     # (64, 2), (64,)

    When the whole dataset is a single tensor in memory, as for our character corpus in lesson 20, it's simpler and faster to index random rows directly: idx = torch.randint(0, N, (B,)); xb, yb = X[idx], Y[idx].

    7. Shape debugging, systematically

    Most PyTorch bugs are shape bugs. Worse, broadcasting turns many of them into silent wrong answers instead of errors. A routine that works:

    1. Write the shapes in comments on every line: # (B, T, C). Name the dimensions.
    2. Run one tiny batch with distinct sizes (B=2, T=3, C=5), so that a transposed pair of dimensions can't hide by being equal.
    3. Assert the shapes you expect: assert logits.shape == (B, V).
    4. Watch the silent broadcasts. (N,) - (N, 1) is (N, N), not (N,). Use keepdim=True in reductions you'll broadcast back.
    5. Know the conventions. F.cross_entropy wants logits of shape (N, C) and targets (N,). For sequences, flatten (B, T, V) to (B·T, V) first.
    Worked example: a silent broadcasting bug

    You compute an MSE with pred = model(x) of shape (N, 1) and targets y of shape (N,). Then ((pred - y) ** 2).mean() broadcasts (N, 1) - (N,) to (N, N). It compares every prediction with every target and averages $N^2$ numbers. No error, a plausible-looking loss, and a model that learns to predict the mean.

    Fix: pred.squeeze(-1) (or y[:, None]), then assert pred.shape == y.shape. With $N = 32$ the buggy loss averages 1024 terms. Run it once with $N=2$ and print the shape, and you'd have caught it immediately.

    8. gradcheck and custom autograd.Functions

    Sometimes you want to supply the backward yourself. It might be faster (a fused kernel), more stable (a hand-simplified formula), or deliberately "wrong" (the straight-through estimator for rounding). That's a torch.autograd.Function: a forward and a backward, glued into the graph as one node, which is literally your Value op with its _backward closure.

    class ScaledTanh(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x, a):                 # y = tanh(a x), a is a 0-d "gain"
        t = torch.tanh(a * x)
        ctx.save_for_backward(x, a, t)
        return t

    @staticmethod
    def backward(ctx, g):                   # g = dL/dy, same shape as y
        x, a, t = ctx.saved_tensors
        local = 1 - t * t
        return g * local * a, (g * local * x).sum()   # one grad per input, same shapes

x = torch.randn(4, 3, dtype=torch.float64, requires_grad=True)
a = torch.tensor(0.7, dtype=torch.float64, requires_grad=True)
torch.autograd.gradcheck(ScaledTanh.apply, (x, a))     # True, or raises with the mismatch

    gradcheck is your workbook-17 numerical-gradient test, built in. It perturbs every input entry, takes central differences, and compares with your backward. Use float64: with float32's roughly 7 significant digits, the difference quotient's rounding error ($\approx 10^{-7}/h$) swamps the comparison.

    Everything from here on (embeddings and RNNs in lesson 20, attention in 22, the GPT you train in 24, and the RL fine-tuning in 26–29) is written in exactly this vocabulary: modules, parameters, a loss, backward(), step(). When something misbehaves, the fallbacks are what you now know: check shapes, check gradients numerically, and check that zero_grad and eval are where they should be.

    9. Problems

    Problem 1
    warm-up

    What is the shape of A + B for A of shape (8, 1, 6) and B of shape (7, 1)? How many elements does the result have?

    Solution

    Right-align: (8, 1, 6) vs (·, 7, 1) → (8, 7, 6), which has $8\cdot7\cdot6 = 336$ elements.

    Problem 2
    warm-up

    Logits are computed as h @ W with h of shape (4, 8, 16) (batch, time, channels) and W of shape (16, 65). What is the output shape, and what shapes must you pass to F.cross_entropy with targets of shape (4, 8)? Enter the number of rows of the flattened logits.

    Solution

    (4, 8, 65). Flatten to logits.view(-1, 65), shape (32, 65), and targets.view(-1), shape (32,). Each of the 32 positions is its own classification problem.

    Problem 3
    warm-up

    How many parameters does nn.Sequential(nn.Linear(784, 256), nn.ReLU(), nn.Linear(256, 10)) have?

    Solution

    $784\cdot256 + 256 + 256\cdot10 + 10 = 200{,}704 + 256 + 2{,}560 + 10 = 203{,}530$. ReLU has none.

    Problem 4
    core

    A contiguous float tensor has shape (2, 3, 4). What is its stride? What is the stride of x.transpose(0, 2)? Enter the three strides of the transposed tensor.

    Solution

    Row-major: the last dim moves 1 element at a time, the middle one 4, the first $3\cdot4 = 12$. So the stride is (12, 4, 1). Transposing dims 0 and 2 swaps their strides: (1, 4, 12), with shape (4, 3, 2) and the same memory. It is not contiguous, since a row-major (4, 3, 2) tensor would have strides (6, 2, 1).

    Problem 5
    core

    You forget opt.zero_grad() and use plain SGD. Suppose the true gradient happens to be the same constant $g$ at every step. The first step moves the parameter by $-\eta g$. By what multiple of $\eta g$ has it moved in total after 3 steps?

    Solution

    The stored gradient after step $k$ is $kg$ (it accumulates), so the moves are $\eta g, 2\eta g, 3\eta g$, for a total of $6\eta g$. In general the effective learning rate grows linearly with the step count, which is why training "goes haywire" in the figure in §5. It's also exactly how deliberate gradient accumulation works: call backward() on several minibatches, then step() and zero_grad() once.

    Problem 6
    core · derivation

    Write the backward of a custom Softplus function $y = \log(1 + e^x)$. What is $dy/dx$ at $x = 0$? Why might you implement the forward as torch.where(x > 20, x, torch.log1p(torch.exp(x)))?

    Solution

    $dy/dx = e^x/(1+e^x) = \sigma(x)$, so backward returns g * torch.sigmoid(x), and at 0 the slope is $0.5$. For large $x$, $e^x$ overflows (float32 overflows past $x\approx 88$), but $\log(1+e^x)\approx x$ there. The where keeps the forward finite, and log1p is accurate when $e^x$ is tiny. One subtlety: torch.where evaluates both branches, and the inf from the unused branch can still poison an autograd-derived gradient. A custom backward avoids that.

    Problem 7
    core

    Your validation loop is for xb, yb in val_loader: total += F.cross_entropy(model(xb), yb), and memory grows until the process dies. Name two independent fixes.

    Solution

    (1) Wrap the loop in with torch.no_grad(): so no graph is recorded at all. (2) Accumulate .item() instead of the tensor. Without either, total is a tensor whose graph links back through every batch's forward pass, so nothing can be freed. Also call model.eval() if the model has dropout or BatchNorm.

    Problem 8
    stretch

    Why does gradcheck insist on float64? Estimate the error of a central difference $\frac{f(x+h)-f(x-h)}{2h}$ when $f$ is computed with relative rounding error $\varepsilon$ (about $6\times10^{-8}$ for float32, $10^{-16}$ for float64), and find the best $h$.

    Hint

    Two error sources: truncation, $\approx \frac{h^2}{6}|f'''|$ (from Taylor, lesson 05), and rounding, $\approx \varepsilon|f|/h$. Minimize the sum over $h$.

    Solution

    Total error $E(h) \approx \frac{h^2}{6}|f'''| + \frac{\varepsilon|f|}{h}$, minimized at $h\sim\varepsilon^{1/3}$, which gives $E\sim\varepsilon^{2/3}$. For float32 that's $h\approx 4\times10^{-3}$ with an error around $10^{-5}$ in the best case, often much worse, too noisy to distinguish a subtly wrong backward from a right one. For float64, $h\approx5\times10^{-6}$ and $E\approx10^{-11}$, a crisp test. PyTorch's default eps=1e-6 is tuned for float64.

    10. Quick check

    You store your layers as self.layers = [nn.Linear(4, 4), nn.Linear(4, 2)]. What happens?
    Only attributes that are Parameters or Modules (including ModuleList/ModuleDict/Sequential) get registered. A plain list is invisible to .parameters(), .to(device) and state_dict(). It's a silent bug.
    Which order of the loop body is correct?
    The grads must be cleared before backward fills them, and step must read them after. Zeroing between backward and step would update with zeros.
    x is a contiguous (3, 4) tensor. Which of these copies memory?
    Transpose, view and slicing only change shape, stride and offset. .contiguous() on a non-contiguous tensor allocates row-major memory and copies. (Note that x.view(4, 3) is not the transpose: it re-reads the same 12 numbers in order.)
    Your logits have shape (N, C). What should go into F.cross_entropy?
    cross_entropy applies a stable log-softmax itself. Softmaxing first double-applies it, and gives a worse loss with weaker gradients.
